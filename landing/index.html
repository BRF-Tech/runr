IN ONE INSTALL

More than deploy — a complete platform.

Deploy, events, environments, data, networking, access control, supply chain, observability, multi-tenancy and billing calculation — all in the same open-source install. Not a single feature behind a paywall.

D

Deploy

git · CLI · Terraform · GitHub Action · GitLab CI/CD

Every project has its own git remote: push, and it deploys. GitHub App, GitLab and Forgejo / Gitea connections come with commit statuses and a deploy history.

  • A preview environment per pull / merge request, removed on close
  • runr CLI: init · dev · deploy and commands for every feature
  • The brf-tech/runr provider on the Terraform Registry, a GitHub Action and a GitLab CI/CD job
  • Image uploads: docker save, OCI tars, .wasm — also for regions without internet
E

Triggers + Events

Webhooks · Topics · Kafka · NATS · CDC

Every project has a list of triggers: HTTP, schedules in a time zone, queues, a webhook inbox, fan-out topics and platform events. The project's event gateway delivers each event as a CloudEvent, with retries and dead letters.

  • Broker and external sources: Kafka, NATS JetStream, RabbitMQ, MQTT, Postgres CDC, S3 and e-mail over IMAP
  • An event is acknowledged only once it is delivered or dead-lettered
  • Webhook signature presets and a generic HMAC; stored events can be replayed
  • Credentials are write-only trigger secrets
P

Environments + Rollouts

dev · staging · prod · blue-green · canary

A project runs in several environments, each with its own URL, configuration overrides, secrets, bindings and region. Promotion moves the same image to the next environment after a preview of what changes; promotions into production wait for approval.

  • A git branch per environment: a push deploys it
  • Blue-green and canary rollouts with test URLs and health checks
  • A canary rolls back by itself when the new revision's error rate or p95 latency crosses its threshold
  • Timed warmer: containers kept warm on a weekly schedule
  • Rollback with the configuration a version ran with
N

Network + Global

Internal network · Global DNS · API keys

Projects of a region call each other by name on an internal network, admitted only by the callee's allow list. A project is public, public to an IP allow list, or internal only.

  • Global projects: one host name across several regions, HA or proximity mode, failover
  • A dedicated Postgres binding of a global project replicated to every region; switchover without data loss
  • API product: consumers, API keys, JWT routes, rate-limit plans and measured usage
  • cert-manager set up in every region for custom-domain certificates
B

Data + Workflows

KV · S3 · Postgres · Workflows

Bindings attached to projects: managed KV (Redis), object storage (Garage or an external S3) and Postgres (CloudNativePG). Credentials arrive as environment variables, with rotation, retention and restore.

  • Durable workflows resume after crashes, redeploys and sleeps of days
  • Steps, retries, timers, events, child workflows
  • Python (runr-workflows) and TypeScript (@runr/workflows) SDKs
  • Per-organization quotas and usage metering
  • Organization export and import: one versioned file — another installation or disaster recovery
R

Access + Security

RBAC · SSO · Secrets · Audit

One permission catalog: built-in and custom roles, groups, per-project access and API tokens limited to a subset of their owner's permissions. SSO groups map to RunR groups and roles.

  • SSO: Google, GitHub, Microsoft, GitLab, OIDC, SAML 2.0
  • Every stored secret encrypted at rest, with key rotation
  • Secret variable values live in the region (Kubernetes Secret or OpenBao), not in RunR's database, or are read from your own secret store: HashiCorp Vault / OpenBao, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault
  • Signed runtime patch feed: the level, reason and CVEs of every runtime patch, and a deadline for critical ones
  • Append-only audit log: CSV / JSON export, SIEM forwarding
S

Supply Chain + Residency

SBOM · Scan · Sign · Admission

Every image RunR builds or receives gets an SBOM (SPDX, CycloneDX), a vulnerability scan (also with an offline database) and a cosign signature with the region's key.

  • A policy gate before deploy
  • Signed-image admission in the region, re-scans of deployed images
  • WebAssembly apps are signed and verified too
  • Data residency: organizations limited to allowed regions and data locations
O

Observability

OpenTelemetry · Tempo · Prometheus · Loki

An OpenTelemetry Collector and Grafana Tempo per region (or your existing backend), auto-instrumented functions and a Traces tab with search and waterfall; metrics and logs per project.

  • Request replay: re-run a captured failed request, diff the response
  • Uptime checks run by the region agent
  • A public status page per organization
  • Alert channels and rules
  • k6 load tests from inside the region: p50 / p95 / p99 latency, errors, pods and cold starts
  • Rightsizing: size recommendations from what the pods really used, applied with one click
T

Multi-Tenant + White-Label + Billing

Tenancy · Branding · Billing API

A PostgreSQL schema per tenant, quotas per region. The brand of the installation and of each tenant without a rebuild; self-service signup with e-mail verification.

  • Billing module, with or without tenancy: a monthly bill per project, pay-as-you-go or fixed-resource regions
  • Tenants resell the regions the platform shares with them to their own projects, with a markup
  • Your own billing system invoices: billing API + signed webhooks
  • A monthly cost limit per project: notify or stop
  • Support tickets with attachments, assignment and real-time updates
  • Single-tenant or multi-tenant edition

Deploy strategies

Blue-green and canary, with an automatic brake.

Pick a strategy per function. Blue-green starts the new revision next to the serving one, with 0 % of the traffic and a test URL of its own, then moves all traffic at once: by hand, or by itself once the health check passes. Canary raises the new revision's share in steps (10 % → 50 % → 100 % by default); when its error rate or p95 latency crosses the threshold during a step, the rollout rolls back on its own.

  • The previous revision stays warm: a rollback is instant
  • Thresholds per function: error rate, p95 latency, time per step
  • The same settings in the console, the CLI and the Terraform provider

Environments and promotion

dev, staging, production: one project, promoted step by step.

A project runs in several environments, each with its own URL, configuration overrides, secret variables, bindings, custom domains, git branch and region. Promotion moves the same code version and image to the next environment, never built again, with the target's own configuration; a preview shows what will change, and promotions into production wait for an approver by default.

  • A git branch per environment: a push deploys that environment
  • Preview environments per pull request stay separate and are removed on close
  • Rollback with the configuration a version ran with

Global projects

One host name, several regions, failover included.

A global project runs in several regions behind one host name. In HA mode the primary region answers while it is healthy and the others take over when it is not; in proximity mode the healthy region closest to the client answers. When the primary fails, RunR fails over to the next healthy region: the Postgres replica there is promoted, and the triggers and the DNS follow.

  • Dedicated Postgres bindings replicated to every region; switchover without data loss
  • Health checks per region; switchover by hand or through failover
  • Managed KV, object storage and shared Postgres stay in their region

Every event a project reacts to, in one list.

Durable workflows

Functions that outlive crashes, redeploys and sleeps of days.

A workflow is an ordinary function in a project, written step by step. Every step's result is recorded, so a run continues where it left off after a crash or a redeploy; a workflow can sleep for ten minutes or ten days, wait for an event, retry a failing step and call other workflows. The console shows every run with its steps and timings.

  • Python (runr-workflows) and TypeScript (@runr/workflows) SDKs
  • A language-neutral protocol: any runtime can implement it
  • Per-organization quotas and usage metering

Supply chain and secret stores

Know every image you run; keep secrets out of the database.

Every image RunR builds or receives gets an SBOM (SPDX and CycloneDX, attached as OCI referrers), a vulnerability scan that also works with an offline database, and a cosign signature with the region's key. A policy gate decides before deploy, and the region admits only signed images. Secret variables never land in RunR's database: they live in the region's Kubernetes Secrets or in an OpenBao RunR runs there, or stay in your own HashiCorp Vault / OpenBao, AWS Secrets Manager, GCP Secret Manager or Azure Key Vault, read with the region's identity.

  • Signed runtime patch feed: the level, reason and CVEs of every patch, deadlines for critical and zero-day ones
  • Dynamic Postgres credentials: short-lived database users from the region's OpenBao
  • Append-only audit log with export and SIEM forwarding

Source code to pod. No container required.

Write the handler, not the Dockerfile. RunR takes your source — a single file or a whole project, from the web editor, git push or the CLI — installs its dependencies, compiles Go, builds the image inside your cluster with Kaniko and hands it to Knative.

Paste code → Deploy

RunR installs dependencies, compiles Go, builds the image in-cluster with Kaniko and ships it to Knative.

1Write code in the web editor or git push — every change is a version
2Hit deploy, run runr deploy or let the push deploy

Behind the scenes: dependency install or Go compile → Kaniko build as a Kubernetes Job (linux/amd64) → push to the region's registry → Knative revision. Code without dependencies skips the build and goes live straight from a ConfigMap.

⚡ ~3 s (no dependencies) · ~23 s (with a build) / change

RunR measurement: v0.4.2, single-node k3s (8 vCPU, 16 GB); median from save until the new code answers (n=3). No dependencies 2.7 s (2.7–3.7 s); with a build 23.0 s (22.0–25.0 s; Kaniko, Node + 1 npm dependency, base images from the region registry cache). A project's first-ever build adds a one-time base-image fetch.

Built-in runtimes

Python Node.js Go PHP PyTorch TensorFlow

Runtime images track upstream: every version that hasn't reached end-of-life is available, and each project picks its own.

Any language: runtime plugins

C Rust Bash Q your language

A runtime is a runtime.yaml manifest plus an image. The universal wrapper (runr-wrapper) turns HTTP requests, queue messages and schedule ticks into invocations over stdin / stdout, in http, exec or persistent mode. Platform administrators and organizations register their own runtimes; runr dev runs them locally on the same images.

WebAssembly (Spin)

Rust Go (TinyGo) JavaScript / TypeScript Python wasm-exec: C / C++ · Zig · .wasm

Wasm functions run as Spin components on runwasi's Spin shim, installed per region in one click from its Isolation tab. wasm-exec runs any WASI command on Spin's WAGI executor.

⚡ From zero to first response: Rust 1.54 s · JavaScript 2.12 s

S

Sandbox API

gVisor · Kata · warm pools · SDKs

Isolated, short-lived sandboxes for the code AI agents write: under the region's strongest isolation (a Kata micro-VM on nodes with KVM, otherwise gVisor), without network access by default, with their own CPU, memory and disk limits.

  • Exec as JSON, Server-Sent Events or WebSocket, also on a terminal (TTY); files, background processes
  • A code interpreter, a console terminal and runr sandbox exec -it
  • Warm pools, pause / resume, TTL, quotas and usage metering
  • Python (runr-sandbox) and TypeScript (@runr/sandbox) SDKs

📉

Scale-to-Zero

Knative-powered: idle pods scale to zero. Replicas reach zero ~60 s after the last request and the pod is gone by ~93 s (RunR v0.4.2 measurement; Knative defaults: 60 s stable window + 30 s grace period). Idle functions hold no resources; the capacity is freed for other workloads.

A region admits scale-to-zero projects against an overcommit budget — by default 3× its CPU and 1.5× its memory, set per region — while always-on projects reserve their full size.

🏢

Multi-Tenant + RBAC

Schema-per-tenant isolation and quotas per region; built-in and custom roles, groups, SSO group mapping and scoped API tokens.

🛡️

Sandbox Isolation

Chosen per project type in each region: gVisor for syscall-level isolation, Kata Containers micro-VMs (Cloud Hypervisor, QEMU, Dragonball, Firecracker; on nodes with hardware virtualization) or plain runc.

SANDBOX & RUNTIME ISOLATION

When you need to change what's beneath the container.

Each region maps XaaS, FaaS, CaaS and build jobs to a container runtime of their own via RuntimeClass: runc by default, gVisor or Kata once installed. gVisor intercepts syscalls, Kata runs each pod in its own micro-VM, and Firecracker (the same Lambda uses) is the most minimal micro-VM of them. The same isolation protects the sandboxes of the Sandbox API.

⚙️

Containerd shim selection — per project type

Each region maps XaaS, FaaS, CaaS and build jobs to a runtime of their own — runc by default, gVisor or any Kata hypervisor as soon as it is installed. On deploy the Knative manifest gets the matching runtimeClassName (gvisor, kata-clh, kata-qemu, kata-dragonball, kata-fc) automatically; WebAssembly functions run on the Spin shim with wasmtime-spin-v2.

🔧

Cilium sandbox network fix — solved in-platform

Sandbox pods can't reach ClusterIP services from the host-net namespace by default (Cilium upstream bug). RunR auto-applies bpf-lb-sock-hostns-only: true on the cluster — non-disruptively, on a running cluster.

RunR is software you install, not a hosted service: the control plane and every region run on infrastructure you operate — bare metal, a private cloud or managed Kubernetes, connected or air-gapped.

Helm Kubernetes

The control plane as one Helm chart: gateway, UI, API, workers, scheduler and Reverb, plus PostgreSQL and Redis unless you point it at your own.

The chart is in BRF's public Helm repository: no credentials needed, and domain is the only required value.

helm repo add brf-tech https://helm.brf.sh
helm repo update
helm upgrade --install runr brf-tech/runr \
  -n runr --create-namespace \
  --set domain=runr.example.com

FAQ

Frequently Asked

What exactly is RunR?
RunR is an open-source serverless platform on Kubernetes and Knative, developed by BRF Teknoloji under the MIT license. You deploy single-file functions (XaaS), multi-file projects (FaaS), containers (CaaS) and WebAssembly from the web console, with git push, from the CLI, Terraform or a GitHub Action — with sandboxes, durable workflows, bindings, GPUs and MCP built in. Think of it as your own AWS Lambda + ECS, on Kubernetes clusters you control.
Is RunR a hosted service?
No. RunR is software you install: you set up the control plane with Helm or with Docker Compose on a single host, then add your own Kubernetes clusters as regions. Your code, data and logs stay on your infrastructure.
Is it really free? Where does money come from?
Yes. MIT license, no feature gates, not open-core: tenancy, SSO, RBAC, the audit log, billing calculation and observability all ship in the same repository. Revenue comes from enterprise support and SLA guarantees for teams that want them.
How do I install it?
On Kubernetes with the chart from BRF's public Helm repository (helm repo add brf-tech https://helm.brf.sh, chart brf-tech/runr; Helm install), on a single host with Docker Compose (single-host guide). The runr CLI installs with curl -fsSL https://runr.sh/install.sh | sh or downloads from runr.sh/dl; the Terraform provider is brf-tech/runr on the Terraform Registry (runr.sh/brf-tech/runr for OpenTofu). Details in the install section above and in the documentation.
How is it different from raw Knative?
Knative is the engine; RunR is the car. Knative gives you primitives, but you still write YAML, build images, manage deployments and set up isolation and monitoring. RunR wraps it in a console and an API: versions, one-click or git push deploys, sandboxes, live logs and traces, roles, billing calculation, multi-tenancy — all included.
Can I run without multi-tenancy?
Yes. Multi-tenancy is a toggleable module (TENANCY_ENABLED=false). When off, the platform runs single-tenant: user management, roles and groups still work and multiple users can use it, just without tenant isolation.
Can one project run in several regions?
Yes. A global project runs in several regions behind one host name: in HA mode the primary region answers while it is healthy, in proximity mode the closest healthy region. A failed primary fails over to the next region with its triggers and data; dedicated Postgres bindings get a replica in every region. Details: global projects.
How secure is code execution?
Every project type runs in the sandbox its region assigns: plain runc, gVisor (a user-space kernel) or Kata Containers (a micro-VM per pod, on nodes with hardware virtualization). On top: RBAC with scoped tokens, secrets encrypted at rest, an append-only audit log, SBOMs, scans, signatures and signed-image admission in the region. Projects are isolated from each other on the internal network too: one project reaches another only through its allow list. Tenants get CPU, memory and GPU quotas per region.
How hard is it to migrate from AWS/GCP/Azure?
Not very. Lambda handlers map 1:1 to XaaS (remove SDK, paste). Cloud Run containers work as-is in CaaS (same Knative base). Azure needs SDK removal. Most migrations take hours, not weeks — the migration cards above show what each platform needs.
Is it production-ready?
Yes. RunR is actively deployed in production on multi-node K8s clusters — multi-tenancy, real workloads, automated CI/CD. PDB, HPA, health checks, automatic migration and rollback support are all included, and installations upgrade in place with helm upgrade.
How do I report a security issue?
Privately, by e-mail to security@runr.sh — not in a public issue. We acknowledge reports within three business days; details in the security policy.
